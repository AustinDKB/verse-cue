# Getting Real Judgment Aid

## Default decision path

| Question | Default | Change course when |
|---|---|---|
| What should we build? | Solve a problem the team understands firsthand. | No one feels the problem. Find a real user and evidence. |
| What is the product? | Write a one-point vision and a three- or four-word mantra. | The sentence cannot reject a feature or settle a choice. |
| Who builds version 1.0? | Use the **Three Musketeers**: developer, designer, sweeper. | Three people cannot build it. Change the team or cut the version. |
| What fits the release? | Fix time and budget. Flex scope. Cut the proposal in half, then cut again. | The core scenario still does not work. Remove more. |
| What comes first? | Interface first, then epicenter, then supporting parts. | A detail blocks use. Fix that detail now. |
| When do we ship? | Ship byte-size pieces when core scenarios work. | A life- or finance-critical system needs additional precautions. |

## Feature gate

1. **New request** → start with **no** or “not now.”
2. **Wait** → apply the **Fight Club** porch test for three days.
3. **Repeated request** → ask whether it fits the one-point vision and changes behavior.
4. **No behavior change** → say, “It just doesn’t matter.” Use the sufficient result.
5. **Possible yes** → map the feature loop, including support, promises, pricing, and maintenance.
6. **Cost exceeds proven value** → reject it, find a human solution, or make a programmer counteroffer.

**Tell**: A request list, many settings, or “simple” tabs that need many related objects signal hidden scope.

## Evidence before commitment

| Signal | Decision |
|---|---|
| Hypothetical scale, staffing, or capacity | Defer it. It is a problem when it is a problem. |
| No load data | Use the simplest setup. Basecamp used one server for its first year. |
| Weeks or thousands of lines for one feature | Listen to the code. Search for a one-hour path instead of a twelve-hour path. |
| A useful shortcut | Record code or design debt and schedule principal payment. |
| A long specification | Replace it with a one-page story, screens, HTML, or a live prototype. |
| A document that will not become an artifact | Do not create the dead document. |

## Team and time rules

- Protect a contiguous half-day for **Alone Time**. The source example used 10 a.m. to 2 p.m.
- Hold a meeting only for an important issue needing input, approval, or agreement.
- Set a 30-minute meeting timer and invite the fewest people possible.
- Before hiring, remove the work, change the practice, try a software slice, then hire.
- For a candidate, prefer actions over words. Use a small paid test, about 20 or 40 hours when possible.
- Hire the better writer when candidates are otherwise close.

## Interface checks

- Review every screen in regular, blank, and error states.
- Use real words and real data. Do not let test data hide the blank slate.
- Put help at the confusion point. Aim for **Zero Training**.
- Prefer context over consistency. Remove controls that do not help the next step.
- Keep regular and administrative work in **One Interface**.

## Launch and customer rules

| Situation | Default |
|---|---|
| Before launch | Use teaser, preview, launch, and a permission list. |
| First offer | Give a useful free sample without a large commitment. |
| Signup | Keep it short and credit-card-free. |
| Cancellation | Make it visible, voluntary, and free of intimidation. Export customer data. |
| After launch | Plan a major update in about 30 days. Keep product posts coming at least weekly. |
| Public status | Use private beta for controlled testing. Release publicly when the product meets its quality bar. |
| Strong reaction | Wait 24–48 hours before changing course. Loud negative voices are not the majority by default. |
| Support | Answer quickly, even before the final repair. The source benchmark was 90% within 90 minutes. |

## Fast smells

- A 12-month roadmap, a 15-box cluster, or a large team before real demand: premature mass.
- A feature added for novelty: feature blight or the bloat monster.
- A meeting used because the idea is hard to explain: simplify the idea first.
- A support wall between builders and users: lost context.
- A bug list without reach and severity: panic instead of judgment.
- A narrow request that consumes work for 7% while harming the other 93%: compare opportunity cost before saying yes.
- A product that needs a manual for ordinary use: simplify before adding training.
