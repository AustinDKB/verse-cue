# Chapter 60: Don't Do Dead Documents

## Core Idea
Eliminate paperwork that does not become part of the real product. Build an interface or prototype when a screen can explain more than a long document.

A document is useful only when it changes into something real. A wireframe that becomes the design has purpose. A wireframe that stops as a separate file becomes dead work. Software changes through discussion, quick decisions, building, and user testing, so no document can capture every decision in advance.

## Frameworks Introduced
- **Build, Do Not Write — Jason Fried, David Heinemeier Hansson, and Matthew Linderman**: Replace explanatory documents with artifacts that move toward the application.
  - **When to use**: Use it when a team needs to explain an interface, feature, or behavior.
  - **How**: Mock up the interface, make a prototype, or build the smallest real version. Keep written material only when it guides that artifact.
- **Document-to-Artifact Test — Jason Fried, David Heinemeier Hansson, and Matthew Linderman**: Keep a document only when it will directly evolve into the product.
  - **When to use**: Use it before creating a wireframe, specification, requirements file, or long email.
  - **How**: Ask whether the document will become a design, code, or another working artifact. If it will stop as a separate file, remove it.
- **No One Is Going to Read It — Gina Trapani, web developer and editor of Lifehacker, from “No One’s Going to Read It”**: Long specifications and standards often gather dust while the team builds and tests.
  - **When to use**: Use it when a team plans to solve uncertainty with a multi-page document.
  - **How**: Let the team build, discuss problems, ask questions, and test with users. Record only information that still helps the next real step.

## Key Concepts
- **Dead document**: A file that stops before it becomes a real product artifact.
- **Living artifact**: A sketch, prototype, or code sample that continues into the product.
- **Paperwork**: Written material that adds effort without moving the product forward.
- **Wireframe**: A screen plan that has value when it changes into the actual design.
- **Prototype**: A rough working version that exposes behavior and invites change.
- **Functional specification**: A detailed description that tries to define software before experience supplies enough information.
- **Iteration**: Repeated building, discussion, testing, and change.
- **User testing**: Direct use that reveals issues no document can predict.

## Mental Models
- **Artifact test**: Treat every document as a question about its next real form.
- **Reality over paper**: Let building and use teach the team what the product needs.
- **Information timing**: Delay detailed decisions until the team has information from a working artifact.
- **Garbage-can test**: If a file will end in the garbage can, do not create it as a substitute for progress.

## Anti-patterns
- **Specification theater**: Writing a long plan makes the team feel organized but does not expose product behavior.
- **Dead wireframe**: A wireframe that never becomes the design adds another version to compare and maintain.
- **Unread standards**: Hours spent on coding standards or descriptive emails fail when builders do not use them.
- **Paper certainty**: A document cannot predict the questions, snap decisions, and issues that appear during real work.
- **Documentation delay**: A long vision document delays a prototype and gives the product less room to grow.

## Worked Example
A team must explain a new screen. It can write a long description, or it can mock up the screen and test the flow. If the mockup changes into the actual design, the work remains useful. If the wireframe stays in a folder while developers code from discussion and user tests, it becomes dead. The same test applies to a product specification, business requirements document, descriptive email, or coding standards file. Build the smallest artifact that answers the next question.

## Key Takeaways
1. Keep written work only when it moves directly toward a real artifact.
2. Replace long explanations with mockups, prototypes, or working code.
3. Use user testing and discussion to handle changing product questions.
4. Delay detailed decisions until building supplies information.
5. Delete documents that remain separate from the application.
6. Treat unread paperwork as a signal that the team needs a closer-to-reality artifact.
