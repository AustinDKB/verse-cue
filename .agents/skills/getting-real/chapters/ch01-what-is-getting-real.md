# Chapter 1: What is Getting Real

## Core Idea
Getting Real is a smaller, faster, better way to build software. It replaces plans and representations with the real interface, then uses launch, feedback, and iteration to deliver only what customers need.

## Frameworks Introduced
- **Getting Real**: Use this approach when an idea must become usable web-based software. Skip charts, graphs, boxes, arrows, schematics, wireframes, and other representations that stand in for the product. Start with real screens, then build the software behind the customer experience.
- **Less**: Use less as a filter for every part of the work. Remove mass, software, features, paperwork, and other items that do not serve an essential customer need.
- **Interface first**: Start with the screens that customers will use. Build backward from that experience so the interface becomes correct before the supporting software becomes complex.
- **Iteration and low change cost**: Launch, tweak, and improve repeatedly. Web-based software supports day-to-day change, so use that advantage instead of waiting one or two years for a boxed-software update.
- **Vigorous writing**: William Strunk Jr., in *The Elements of Style*, gives the related writing rule. Use concise writing in plans, product text, and communication. Remove unnecessary words so each word tells.

## Key Concepts
- **Real thing**: The working product that customers see and use, rather than a plan about that product.
- **Functional spec**: A temporary document that can create an illusion of agreement instead of showing product reality.
- **Customer experience**: The interface and behavior that customers actually encounter.
- **Less**: The deliberate removal of nonessential work and product mass.
- **Iteration**: Repeated launch, adjustment, and improvement.
- **Web-based software**: Software that can evolve from day to day after launch.
- **Bloat**: Unneeded timelines, features, options, paperwork, meetings, hierarchy, and other process weight.
- **Getting Real process**: A big-picture approach that favors real screens, small teams, rapid prototyping, and expected iteration.

## Mental Models
- **Reality over representation**: When a functional spec and a real webpage disagree, trust the webpage because customers use it.
- **Start at the experience**: Treat the customer-facing screen as the starting point, not the final output of an internal plan.
- **Change as an advantage**: Treat each iteration as a way to lower the cost of finding and correcting a wrong decision.
- **Less as a decision test**: If an item does not help customers, question its place before adding more software, process, or staff.

## Anti-patterns
- **Bureaucratic process**: Long timelines, excessive paperwork, and meetings create slow, murky, changeless software.
- **Pie-in-the-sky functional specs**: Abstract agreement can hide the actual problems in the interface.
- **Building for every preference**: Endless options and preferences add mass without proving customer value.
- **Planning the perfect future**: Pristine roadmaps and meaningless version numbers replace direct learning from the product.
- **Premature scale and staffing**: Scalability debates, dozens of employees, and top-down hierarchy add weight before the product needs it.
- **Detached validation**: Unrealistic user testing and outsourced support separate the team from the real customer experience.

## Worked Example
A team can begin with a real page instead of a functional spec, roadmap, or wireframe set. The page shows the customer experience and exposes interface problems early. The team then builds only the software needed behind that page, launches it, and improves it through small iterations. The team removes options, paperwork, and other work that does not help the customer. This example captures the chapter's sequence: start with reality, build less, launch, and learn.

## Key Takeaways
1. Build the real interface instead of spending time on representations of the product.
2. Start with what customers experience, then build the supporting software backward from that point.
3. Use less mass, fewer features, and less process to keep the team small and agile.
4. Launch, tweak, and improve because web software can change day by day.
5. Base software decisions on the real product, not on abstract agreement.
6. Apply the same small-team, rapid-prototyping, and iteration ideas to other work when useful.
