# Chapter 22: It Just Doesn't Matter

## Core Idea
Great products determine what matters and leave out the rest. If a requested detail does not change user behavior or provide essential value, the team can say, “It just does not matter.” This rule removes work, support cost, processing cost, and learning cost.

## Frameworks Introduced
- **Essentials only — Jason Fried, David Heinemeier Hansson, and Matthew Linderman**: Use this rule to separate necessary behavior from attractive extras.
  - **When to use**: Use it whenever someone asks why the product does not include a precise, decorative, or familiar feature.
  - **How**: Ask whether the feature is essential and whether it changes behavior. If the answer is no, leave it out and provide the simplest sufficient alternative.
- **It just does not matter — Basecamp team**: Use this phrase as a decision rule, not as an excuse to ignore real problems.
  - **When to use**: Use it when a request sounds nice to have but does not improve the product's central work.
  - **How**: Measure the effect on user action. Count the cost of extra software, support, processing, and learning. Keep the feature out when its benefit does not justify those costs.
- **Behavior test — Jason Fried, David Heinemeier Hansson, and Matthew Linderman**: Use behavior change as the test for importance.
  - **When to use**: Use it when the team debates extra precision or information.
  - **How**: Ask, “If this value changes, will the user act differently?” If not, choose the sufficient result.

## Key Concepts
- **Essential**: Necessary for the product's main work.
- **Sufficient**: Enough to support the user's real need.
- **Behavior test**: A test that asks whether a detail changes what users do.
- **Nice-to-have**: A pleasing addition that does not provide necessary value.
- **Feature cost**: The added software, support, processing, and learning work.
- **Subtraction**: Product improvement created by removing irrelevant work.
- **Precision**: Extra exactness in time, count, or presentation.
- **Productivity gain**: Time recovered by removing work that does not matter.

## Mental Models
- **Behavior over precision**: Prefer a less exact value when greater precision changes no action.
- **Sufficient beats elaborate**: Use the simplest solution that meets the real need.
- **Every feature has a shadow**: Count support, processing, and learning costs along with the visible feature.
- **Subtraction creates capacity**: Removing irrelevant work gives the team more time for important work.

## Anti-patterns
- **Precision for its own sake**: More exact values consume time without changing decisions.
- **Formatting by default**: Bold, italic, and color add software and support work to a text chat without essential value.
- **Counting without behavior**: A total number adds little when names already show who is present.
- **Working on irrelevant details**: Time spent on work that does not matter reduces productivity.
- **Calling every request essential**: The product loses focus when nice-to-have work receives equal status.

## Worked Example
Campfire used five-minute timestamps instead of a timestamp on every chat line because second-by-second or minute-by-minute tracking rarely changes behavior. It did not add bold, italic, or colored chat formatting. Users could use capital letters or a few asterisks without extra software, support, processing, or learning. It listed each person's name instead of showing the total room count because the total did not change what users did. These omissions were deliberate because the extra precision and formatting did not matter.

## Key Takeaways
1. Test each feature by asking whether it changes user behavior.
2. Choose a sufficient result instead of extra precision.
3. Count the support, processing, and learning cost of every addition.
4. Use simple existing behavior when it meets the need.
5. Protect time for work that changes the product's main result.
