# Chapter 29: Race to Running Software

## Core Idea
Get real software running as soon as possible. Running software creates momentum, exposes weak ideas, produces real reactions, and helps different people reach agreement better than stories, wireframes, or arguments about sketches.

## Frameworks Introduced
- **Race to running software — Jason Fried, David Heinemeier Hansson, and Matthew Linderman**: Make a working product the first project priority.
  - **When to use**: Use it from the first day of a project and at the component level inside the project.
  - **How**: Do less, skip low-value detail, and take safe shortcuts when they produce running software faster. Use the working result to decide what deserves attention next.
- **The real thing leads to agreement — Christopher Alexander**: Use full-scale real work to bring different opinions together.
  - **When to use**: Use it when people disagree about sketches, ideas, or descriptions of a future interface.
  - **How**: Make the real thing, observe the reactions, and let shared contact with the result replace abstract argument. Agreement tends to converge around what people can see and use.
- **Get it working ASAP — Matt Hamer**: Apply the priority at every scale.
  - **When to use**: Use it for the whole application and for each important component or interface.
  - **How**: Build a working component early, let other developers try it, and use the collaboration to define interfaces and features that meet actual needs.

## Key Concepts
- **Running software**: A working implementation that people can inspect and use.
- **Momentum**: Forward movement created by a real product and shared progress.
- **True understanding**: Knowledge gained from reactions to working behavior.
- **Approximation**: A story, wireframe, or mock-up that represents a possible result.
- **Real reaction**: Feedback produced by contact with working software.
- **Agreement**: Shared understanding that emerges from examining the same result.
- **Fractal mantra**: The rule “get something real up and running” applied at every scale.
- **Working component**: A usable part of the product that helps define surrounding interfaces.

## Mental Models
- **Software as a truth test**: Use a working result to replace speculation with evidence.
- **Agreement through contact**: Let people react to the same artifact instead of defending separate descriptions.
- **Small-scale mirror**: Apply project-level speed to each component and interface.
- **Shortcut toward learning**: Skip low-value process when it delays the first useful reaction.

## Anti-patterns
- **Planning without development**: Spend a long period discussing features before any working implementation exists.
- **Sketch argument**: Treat a wireframe or paragraph as if it proves how the product will work.
- **Detail-first process**: Polish minor details before testing the central behavior.
- **Perfect-before-use**: Delay a component until it is complete, then discover that its interface does not fit.
- **Abstract agreement**: Seek consensus about descriptions instead of building something people can examine.

## Worked Example
A team can debate a screen through stories, wireframes, and HTML mock-ups, but those artifacts remain approximations. If the team builds a working version, people can react to the real behavior. A developer can also build a key component before the full application is complete. Other developers try to use it, discover how it fits their parts, and help define interfaces that work in practice. The same rule guides the whole project and each component.

## Key Takeaways
1. Make running software the first priority.
2. Use safe shortcuts when they lead to a real result faster.
3. Replace abstract arguments with reactions to working behavior.
4. Apply the rule to components, not only to the full application.
5. Let early implementations expose the interfaces and features that matter.
