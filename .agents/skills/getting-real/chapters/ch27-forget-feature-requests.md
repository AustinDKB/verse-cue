# Chapter 27: Forget Feature Requests

## Core Idea
Let customers remind you what matters instead of maintaining a permanent request database. Read every request, discard the record, and remember only the requests that return often enough to become impossible to forget.

## Frameworks Introduced
- **Forget feature requests — Jason Fried, David Heinemeier Hansson, and Matthew Linderman**: Use customer repetition as the memory system for product priorities.
  - **When to use**: Use it when customers send a large volume of feature requests and the team feels pressure to catalog every one.
  - **How**: Read the request, learn from it, and throw away the record. Let important requests return through repeated customer contact. Reconsider them only when the repeated need also fits the product vision.
- **Let customers be your memory — Jason Fried, David Heinemeier Hansson, and Matthew Linderman**: Replace request tracking with live evidence.
  - **When to use**: Use it when a request list creates analysis work but does not improve decisions.
  - **How**: Listen in real time. Treat daily reminders as stronger evidence than an old count. Keep no special memory for a request that customers do not repeat.
- **Maintain the product vision — Jason Fried, David Heinemeier Hansson, and Matthew Linderman**: Separate demand from permission to build.
  - **When to use**: Use it even after many customers ask for the same thing.
  - **How**: Consider repetition a reason to review, not an automatic yes. Say no when the request would move the product away from its purpose.

## Key Concepts
- **Feature request**: A customer proposal for a product addition or change.
- **Request avalanche**: A large flow of suggestions that can overwhelm product attention.
- **Repeated request**: A need that returns from separate customers or repeated contact.
- **Customer memory**: The live reminder created when users continue to ask.
- **Request list**: A stored record intended to rank future product work.
- **Real-time evidence**: Current user behavior and repeated conversation, not an old count.
- **Product vision**: The direction that limits which requests belong.
- **Automatic yes**: Acceptance based on demand alone, without judgment.

## Mental Models
- **Customer alarm**: A request that matters keeps sounding until the team cannot ignore it.
- **Signal through repetition**: Repeated contact separates durable needs from passing wishes.
- **List as false comfort**: A complete backlog can feel organized while no one uses it.
- **Demand is evidence, not authority**: Customers show importance, but the team still protects the product's direction.

## Anti-patterns
- **Request hoarding**: Save every suggestion and create a growing maintenance burden.
- **Hash-mark theater**: Count requests in a list that the team never reviews.
- **Old-list planning**: Use stale rankings instead of current customer reminders.
- **Popularity equals permission**: Build a feature only because many people ask for it.
- **Forum surrender**: Let the loudest request determine the product vision.

## Worked Example
When Basecamp launched, the team tracked major feature requests on a Basecamp to-do list. Each repeated request gained another hash mark, with the plan to review the most requested items later. The team never returned to the list. Customers kept making the same requests, so the team already knew what mattered next. The repeated requests supplied the memory in real time. The team still retained the right to say no when a popular request did not fit the product vision.

## Key Takeaways
1. Read every request without promising implementation.
2. Discard the record after extracting its useful signal.
3. Watch for requests that return through repeated customer contact.
4. Treat repetition as a prompt for review, not a command to build.
5. Protect the product vision even when request counts increase.
