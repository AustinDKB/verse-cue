## Core Frameworks & Mental Models

Use these rules in this order when a product, team, or release needs a clear decision:

1. **Getting Real** — Use when turning an idea into web software. Start with the real interface, build the supporting software behind it, launch core scenarios, and improve through use.
2. **Less** and **Underdo your competition** — Use when scope grows or competitors add features. Remove mass, options, process, and difficult problems. Solve a smaller problem well instead of matching feature count.
3. **Build software for yourself** and **One-point vision** — Use at the start. Choose a problem you understand, write the product vision in one sentence, and use both as filters for daily decisions.
4. **Pick a fight**, **The anti-Project**, and **Opinionated software** — Use when category habits or competitor lists control the product. Name the rejected approach, state your alternative, and omit features that weaken the product’s point of view.
5. **Fix time and budget, flex scope** and **Embrace constraints** — Use when planned work exceeds available resources. Keep the date and budget fixed, remove lower-value scope, and protect quality. Use limits to expose essential work.
6. **Half, not half-assed**, **Start with no**, **It just does not matter**, and **Hidden Costs** — Use for feature decisions. Cut the proposal in half, begin with no or “not now,” test whether behavior changes, and count implementation, support, documentation, and promise costs.
7. **Human solutions**, **Forget feature requests**, and **Ask people what they do not want** — Use when customers request special controls or more features. Understand the root problem, observe repeated needs, and prefer a general solution or subtraction.
8. **Race to running software**, **Rinse and repeat**, and **From idea to implementation** — Use when debate replaces progress. Start with the large product questions, test paper or HTML, build a working slice, and repeat design, use, analysis, and revision.
9. **Interface First**, **Epicenter design**, and **Three State Solution** — Use before expensive code. Design the core content first, then cover regular, blank, and error states. Let the interface expose scope and effort.
10. **Thoughtful blank slate**, **Context Over Consistency**, **Copywriting Is Interface Design**, **Real Words**, and **Personify Your Product** — Use for interface quality. Design the first-run state, choose controls for the current task, write customer language, use realistic content, and keep one product personality.
11. **Less mass**, **Cheap and fast changes**, **Emergence**, and **Simple rules, complex behavior** — Use before adding commitments. Prefer small teams, simple systems, reversible decisions, open formats, and rules that allow useful behavior to emerge.
12. **Less Software**, **Code Speaks**, and **Manage Code and Design Debt** — Use when a solution grows complex. Reframe the problem, seek a smaller implementation, treat hard code as design feedback, and repay shortcuts before interest grows.
13. **Scale later** and **It is a problem when it is a problem** — Use for hypothetical load, staffing, and capacity concerns. Start with the simplest setup that supports current demand, then respond to evidence from real use.
14. **The Three Musketeers**, **Unity**, **Alone time**, and **Avoid meetings** — Use when organizing work. Start with a developer, designer, and sweeper. Keep specialties connected, protect a contiguous half-day for focus, and hold meetings only for issues that need group input.
15. **Add slow to go fast**, **Need-before-hire test**, **Actions, Not Words**, **Quick-learning generalists**, and **Hire good writers** — Use when adding people. Remove work first, test a small assignment, inspect real work, value learning and range, and use clear writing as evidence of clear thinking.
16. **Test in the wild**, **Feel The Pain**, **Zero Training**, **Answer Quick**, and **Tough Love** — Use after release. Test with real users and data, keep builders near support, repair confusion in the interface, acknowledge messages quickly, and filter requests through product direction.
17. **Hollywood Launch**, **Promote Through Education**, **Easy On, Easy Off**, **Earn It Month to Month**, and **Softer Bullet** — Use for launch and revenue. Build interest before launch, teach useful subjects, make signup and cancellation easy, earn renewals through value, and protect existing customers from surprise.
18. **Publicize Your Screwups**, **Impact-Based Bug Prioritization**, **Ride Out the Storm**, and **Go With the Flow** — Use after failure, controversy, or new evidence. State the facts and repair, rank bugs by harm, wait 24–48 hours before reacting, and follow the stronger path when the first plan loses plausibility.

### Default decision sequence

1. State the one-point vision, key problem, target customer, and enemy.
2. Cut the product until the essential experience fits the fixed time and budget.
3. Design the interface, core content, blank state, and error state before expensive code.
4. Build running software, test it in the wild, and repeat small improvements.
5. Keep the team, process, code, and commitments light enough to change direction.
6. Use customer voices, support work, and observed behavior to choose the next step.
