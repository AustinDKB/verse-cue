# Chapter 12: Map the Scopes

## Core Idea
Organize work by the structure of the project, not by the people doing it. Scopes are integrated parts that can finish independently and become the project's shared language.

## Frameworks Introduced
- **Scopes**: Independent, integrated slices larger than tasks and smaller than the project.
  - When to use: Discover them after the team starts real work.
  - How: Capture tasks first, then factor related tasks into named territories that can finish in a few days or less.
- **Scope map**: A high-level view of the project represented in practice by one to-do list per scope.
  - When to use: Use it when tasks begin to reveal their relationships.
  - How: Create, rename, split, and move lists as the anatomy of the project becomes clear.
- **Language of the project**: Use scope names to discuss progress and dependencies.
  - When to use: Use it for status and sequencing.
  - How: Say which scope is done, which scope follows, and which scope contains a new task.
- **Layer cake**: UI surface area and thin, evenly distributed back-end work can stay in one scope.
  - When to use: Use it as the default for simple information systems.
- **Iceberg**: One side of the work has much more complexity than the other.
  - When to use: Use it when complex back-end or front-end work would hide inside one scope.
  - How: Factor independent UI, back-end, or concern-specific work into separately finishable scopes.
- **Chowder**: A small list for loose tasks that do not fit elsewhere.
  - When to use: Use it only for exceptions.
  - How: Treat more than three to five items as a sign that a scope is missing.
- **Tilde marker (~)**: Prefix a nice-to-have task or scope with `~`.
  - When to use: Use it whenever new improvements appear during the cycle.
  - How: Keep it as optional work that the team can cut without making the core incomplete.

## Key Concepts
- **Scope**: A project part that can be built, integrated, and finished independently.
- **Scope map**: The mental and practical map of those parts.
- **Grab bag**: An unrelated group whose done state is unclear.
- **Junk drawer**: A generic scope such as “bugs” or “front-end” that hides project structure.
- **Interdependency**: A relationship that determines when a part can be finished.

## Mental Models
- Think of scopes as **territories on a map**, not categories for tidy task storage.
- Use the **anatomy test**. A good scope name should identify a real part of the problem.
- Treat `~` as a **scope machete** that separates must-haves from nice-to-haves.

## Anti-patterns
- **Designer and programmer lists**: Role-based lists hide whether a finished product slice exists.
- **Artificial grouping**: Arbitrary categories do not reveal real dependencies.
- **Grab bags and junk drawers**: Generic names prevent a clear done decision.
- **Oversized scope**: A scope that takes too long becomes a hidden project.

## Worked Example
A message-draft project first created the scope **Start New** for the core interaction. Later, the team identified **Locate**, **Trash**, and **Save/Edit**. Deeper work split those into **Send**, **Store**, and **Reply**. The scope names showed the project's anatomy and let the team finish one visible piece at a time. The team could then say which part was done without listing every task.

## Key Takeaways
1. Capture tasks before forcing them into categories.
2. Discover scopes through real work.
3. Keep each scope independent and finishable soon.
4. Use scope names for status and sequencing.
5. Redraw scopes when their done state or name is unclear.
