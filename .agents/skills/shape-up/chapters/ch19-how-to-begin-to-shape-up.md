# Chapter 19: How to Begin to Shape Up

## Core Idea
Adopt Shape Up in one controlled step. Build shipping ability first, then add more shaping, scope mapping, progress views, and cycle structure as the team gains confidence.

## Frameworks Introduced
- **Option A: One six-week experiment**: Test the method with one significant project and one protected team.
  - When to use: Use it when the product team can reserve a designer and two programmers.
  - How: Shape a conservative project, protect the team for six weeks, skip a formal betting table, present the pitch, let the team discover tasks, give them a shared space, and encourage one integrated piece early.
- **Option B: Start with shaping**: Improve the input before changing the scheduling system.
  - When to use: Use it when another leader controls programmer time.
  - How: Shape a compelling, bounded project and send it through the existing process.
- **Option C: Start with cycles**: Give teams longer uninterrupted periods before adding full shaping practice.
  - When to use: Use it when two-week sprints create constant planning overhead.
  - How: Work in six-week cycles, then use the extra room to shape better work.
- **Fix shipping first**: Build the ability to finish and ship before optimizing research or discovery.
  - When to use: Use it when insight does not turn into released work.
- **Focus on the end result**: Judge success by the meaningful result after the cycle, not by idle time or hourly activity.
  - When to use: Use it when autonomy makes managers worry about local utilization.

## Key Concepts
- **Six-week experiment**: A bounded adoption test with one project and one protected team.
- **Shipping muscle**: The team's ability to finish and release work.
- **Uninterrupted time**: The first protection to add during adoption.
- **End result**: The cycle outcome used to judge success.
- **Existing process**: The current scheduling path that can receive better-shaped work.

## Mental Models
- Use a **small experiment** as proof before asking the whole company to change.
- Treat shipping as a **muscle**. Build it before refining the input.
- Judge a cycle at the **macro level**. Local idle time is less important than a valuable result shipped.

## Anti-patterns
- **Big-bang adoption**: A whole-team change creates too much risk before the method has credibility.
- **Research-first perfection**: Better insight has little value if the team cannot ship.
- **Micro-utilization control**: Watching hours undermines autonomous ownership.
- **Tool-first adoption**: Adding Hill Charts before the team can finish a slice adds ceremony without progress.

## Worked Example
For the first experiment, shape one significant project that should fit six weeks with extra margin. Reserve one designer and two programmers, and do not interrupt them. Present the five pitch ingredients at kick-off. Let the team discover tasks and wire UI and code together early. Delay scope maps and Hill Charts until the team understands the value of an integrated slice. Use the shipped result to support a larger change.

## Key Takeaways
1. Choose one adoption path that fits the current constraint.
2. Protect one team before adding more process.
3. Start with one meaningful, conservative project.
4. Add scope mapping and Hill Charts after integrated work feels natural.
5. Focus on the end result after six weeks.
