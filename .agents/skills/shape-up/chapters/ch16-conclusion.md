# Chapter 16: Conclusion

## Core Idea
Shape Up is a connected method, not a list of isolated tools. Its language makes risk, time, scope, uncertainty, and responsibility visible so a team can ship meaningful work without carrying open-ended commitments.

## Frameworks Introduced
- **Shaped versus unshaped work**: Shape before a team receives a fixed cycle.
  - When to use: Use this distinction whenever a project request arrives.
  - How: Require a narrow problem, appetite, solution, risk treatment, and exclusions.
- **Appetite instead of estimate**: Decide the time worth spending before designing the solution.
  - When to use: Use it to create a variable-scope constraint.
- **Capped bet**: Commit one cycle, protect it with uninterrupted time, and apply the circuit breaker.
  - When to use: Use it for work that should ship without a runaway project.
- **Integrated building**: Build one piece, map scopes, show known and unknown work, then hammer scope.
  - When to use: Use the sequence during the cycle.

## Key Concepts
- **Six-week cycle**: The default time horizon for meaningful work.
- **Cool-down**: The recovery and decision period between cycles.
- **Scope**: An independently finishable project part.
- **Uphill and downhill**: The language for unknown work and executable work.
- **Scope hammering**: The practice that turns a fixed deadline into focused trade-offs.

## Mental Models
- Think of Shape Up as a **chain**. A weak link in shaping, betting, or building raises the risk of the whole project.
- Use **language as a control surface**. Terms such as appetite, rabbit hole, scope, and uphill make hidden decisions discussable.
- Think of the method as **guard rails plus judgment**. It supplies boundaries, not a complete script for every detail.

## Anti-patterns
- **Isolated-tool adoption**: A Hill Chart cannot repair a project that lacks a shaped problem and solution.
- **Method as rigid ceremony**: Specific practices can change with team size, but the basic truths remain.
- **Micro-progress worship**: Hours and task counts do not replace a meaningful result shipped.

## Worked Example
A raw calendar request becomes a narrow “see free spaces” problem. The team sets a six-week appetite, shapes the Dot Grid, patches risks, and writes a pitch. The betting table commits one cycle with uninterrupted time. The team integrates the core interaction, maps scopes, moves unknown work uphill first, and marks optional details with `~`. It ships a better baseline without promising an unlimited calendar.

## Key Takeaways
1. Use the terms together, not as separate tricks.
2. Shape before betting and bet before building.
3. Protect the cycle and keep future choices open.
4. Make uncertainty visible and scope variable.
5. Adapt practices to team size without losing the basic truths.
