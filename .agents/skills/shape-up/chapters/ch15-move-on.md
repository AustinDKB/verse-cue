# Chapter 15: Move On

## Core Idea
After shipping, let the initial storm of feedback pass. Keep a clean slate, treat requests as raw ideas, and shape important feedback before making a new bet.

## Frameworks Introduced
- **Let the storm pass**: Feature releases produce requests, bugs, and strong reactions.
  - When to use: Use it immediately after a release, especially after a workflow change.
  - How: Stay calm, wait a few days, and judge feedback against the reason for the change.
- **Stay debt-free**: Do not promise an immediate follow-up just because feedback arrived.
  - When to use: Use it when a request or bug appears after shipping.
  - How: Give it a gentle “no,” keep the option open, and let it compete with other work at the next betting table.
- **Feedback needs to be shaped**: Post-release input is a raw idea, not an actionable project.
  - When to use: Use it when a request may deserve a future cycle.
  - How: Set boundaries, find the specific problem, shape a solution, and present a new pitch.

## Key Concepts
- **Raw feedback**: New input that still lacks an appetite, solution, and boundary.
- **Clean slate**: Freedom to choose the next cycle without inherited promises.
- **New bet**: A fresh commitment for work that needs more time after release.
- **Knee-jerk reaction**: An immediate change made before feedback settles.

## Mental Models
- Treat post-release reaction as **weather**. Observe it before changing direction.
- Treat an immediate promise as **debt** because it removes future choice.
- Use the **next betting table** as the filter for every non-crisis request.

## Anti-patterns
- **Immediate reversal**: A loud minority can make a useful change look like a failure.
- **Promise on contact**: Saying yes turns raw feedback into an unpaid commitment.
- **Carry-over scraps**: A shipped feature's new work bypasses shaping and competes unfairly.

## Worked Example
A release changes an existing workflow. A small group of customers says, “You ruined it.” The team does not reverse the change immediately. It waits several days, checks why the change was made and who it helps, then records the remaining requests as raw ideas. If one request proves important, someone shapes it during the next shaping period and presents it as a new bet.

## Key Takeaways
1. Let intense release feedback settle.
2. Keep the next cycle open.
3. Say a gentle no to raw requests.
4. Shape important feedback before committing more time.
