# Chapter 3: Set Boundaries

## Core Idea
Start with an appetite and a narrow problem, then shape a solution inside those limits. Do not begin with an estimate or an attractive feature label.

## Frameworks Introduced
- **Appetite**: A time budget for a standard team size.
  - When to use: Set it before solution design.
  - How: Choose **Small Batch** for one or two weeks with one designer and one or two programmers, or **Big Batch** for a full six weeks.
- **Fixed time, variable scope**: Appetite starts with a number and ends with a design. An estimate starts with a design and ends with a number.
  - When to use: Use it at shaping and building stages.
  - How: Keep the time fixed, then remove or simplify scope when quality or risk needs room.
- **Good is relative**: The best solution depends on the time and importance of the problem.
  - When to use: Use this rule when people compare a bounded solution with an unlimited ideal.
  - How: Judge the result against the appetite and the customer need.
- **“Interesting. Maybe some day.”**: The default response to a raw idea is a soft no, not a commitment.
  - When to use: Use it when the idea first arrives.
  - How: Keep options open until the problem and solution are shaped.
- **Narrow down the problem**: Replace a broad request with the specific moment where the current workflow fails.
  - When to use: Use it when a request names a feature instead of a pain point.
  - How: Ask when the person needed the feature and what failed in that situation.

## Key Concepts
- **Raw idea**: A request or feature phrase that lacks boundaries and a shaped solution.
- **Small Batch**: A one- or two-week project for a standard small team.
- **Big Batch**: A project that fills one six-week cycle for a standard small team.
- **Grab-bag**: A broad project label with no clear start, end, or definition of done.
- **Baseline**: The way customers solve the problem without the new work.

## Mental Models
- Think of the **appetite** as a creative constraint, not a forecast.
- Use the **customer story** as a baseline for judging a solution.
- Treat a broad label such as “2.0” as a signal to search for smaller problems.

## Anti-patterns
- **Estimate-first design**: It invites a solution that grows before anyone decides its value.
- **Feature-first discussion**: It creates debates about a solution without a test of fitness.
- **Grab-bag project**: “Files 2.0” hides many unrelated problems and makes “done” unclear.
- **Early enthusiasm**: It creates expectations before the idea earns a commitment.

## Worked Example
A customer asked for complex permission rules after someone archived a file and made it disappear for other users. The deeper problem was that the person did not understand the archive action. A warning on the archive action could solve that case in one day. The team did not need a six-week permission system. In the calendar case, a customer story showed the real need: seeing free meeting-room spaces from home, not reproducing every calendar feature.

## Key Takeaways
1. Set the appetite before exploring solutions.
2. Ask what went wrong in a real use case.
3. Prefer a small, specific problem over a broad feature name.
4. Keep time fixed and let scope vary.
5. Require a raw idea, appetite, and narrow problem before finding elements.
