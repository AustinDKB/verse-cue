# Chapter 10: Hand Over Responsibility

## Core Idea
Assign a whole project, not a list of tasks. The shaped pitch sets the boundaries, then a small designer-programmer team defines tasks, makes trade-offs, and deploys the result.

## Frameworks Introduced
- **Assign projects, not tasks**: Keep the project whole and let the team decide its approach.
  - When to use: Use it after shaping and betting.
  - How: Give the team the pitch, the appetite, and responsibility for the complete outcome.
- **Done means deployed**: A project must reach production within the time budget.
  - When to use: Use it for every cycle project and each small-batch project.
  - How: Scope essential work early, coordinate testing inside the cycle, and deploy before the deadline.
- **Kick-off**: Start with the pitch or a distilled shaped concept in the project space, then answer important questions in a team call.
  - When to use: Use it at the start of a remote project.
  - How: Give the team a shared reference and enough context to begin.
- **Getting oriented**: The first days may show no visible progress while people learn the code and find a starting point.
  - When to use: Respect this phase at project start.
  - How: Avoid early status pressure. If silence does not break after about three days, ask what is happening.
- **Imagined versus discovered tasks**: Real work reveals tasks that no one could see from the initial pitch.
  - When to use: Use discovered tasks to replace a false up-front master plan.
  - How: Start a meaningful piece and record new work as the team encounters it.

## Key Concepts
- **Autonomy**: Authority to execute the shaped concept within its boundaries.
- **Appetite**: The time budget that makes “done” meaningful.
- **Discovered task**: Work revealed by interaction with the real system.
- **Kick-off message**: The shared project reference for the shaped concept.
- **Small batch**: Several short projects that one team deploys before the cycle ends.

## Mental Models
- Think of the pitch as an **outline** that talented people fill with real decisions.
- Treat early silence as **orientation work**, not as failure to produce.
- Think of task discovery as a property of real work, not a planning defect.

## Anti-patterns
- **Up-front task decomposition**: It disconnects parts and hides responsibility for integration.
- **Early status interrogation**: It interrupts the exploration needed to find a good starting point.
- **Absolute freedom**: A team should not invent an unshaped project from scratch.
- **Done without deployment**: A finished task list does not honor a cycle bet.

## Worked Example
A designer and programmers begin with a pitch posted to a Basecamp project. During the first few days, they inspect the relevant code and test short starting points. The designer may discover that a new desktop button has no mobile location. The programmer may find a model method that needs a later update while tracing database associations. They record these discovered tasks instead of pretending the pitch could list them in advance.

## Key Takeaways
1. Give the team the whole project and its boundaries.
2. Let the team define tasks from real work.
3. Respect the orientation phase.
4. Treat deployment as the meaning of done.
5. Keep testing inside the cycle.
